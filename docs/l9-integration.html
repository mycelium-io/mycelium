How mycelium integrates L9

L9 is the epistemic layer of the Internet of Cognition: a fixed message envelope (kind/subkind, participants, episode URN, causal message.parents, typed payload) that carries cognition between agents and engines. Mycelium is one producer of those envelopes.

The pieces, one local integration:

  • ioc-protocols-models: the L9 spec plus the generated language bindings. The grammar. Mycelium vendors the python binding as l9_models.py.
  • AGNTCY SLIM: the transport, one MLS-encrypted group channel per room. L9 envelopes ride SLIM as additive JSON. The wire.
  • the aligner: a first-party mediator (NEGMAS Stacked Alternating Offers, with a persistent Pi session as its brain). It negotiates issue by issue and emits exchange and commit envelopes.
  • the conductor: a first-party engine with no model of its own that walks a flow inside a task's thread. Two of its built-in flows are cut-down versions of L9's own protocols: Concord (help members agree) and Accord (get on the same page before work starts).
  • mycelium backend: the room's moderator. It synthesizes the envelopes from the parsed replies, records every episode, and computes the numbers. Agents never speak L9 themselves.

The load-bearing fact: mycelium's L9 envelopes are additive and never required of agents. Agents post plain prose, optionally ending with one marker ([[mycelium: confidence=0.8 stance=accept]], or [[mycelium: A=82 B=41]] when a flow asks for ratings), and the backend lifts that onto the envelope it synthesizes.

Both ways to agree run inside a task. A task is a board row and a thread; an agreement is one episode nested in that thread, recorded at log/episodes/{id}.md. When it converges, the follow-up work lands on the board as sub-tasks of the task it ran in.

Concord: help members agree

L9's Concord, cut down to what a room needs to settle one decision. Everyone suggests one option, everyone rates every option, and code picks. A model is in each node (a member writing an option or a rating); the edges are code. 

mycelium board coordinate work/acme-renewal-offer conductor \
  "concord @success @finance @sales @legal: Decide the renewal offer for Acme."

or, in the task's thread in the app: @conductor concord @success @finance @sales @legal: …

The pick

  • Leximin. Each option's ratings are sorted lowest first and compared option against option; the larger vector wins, ties go to the earlier letter. The pick is the option the least happy member likes best, so nobody gets steamrolled.
  • Feasible when every member rated the pick at or above the bar (70 by default).
  • Infeasible when someone rated it below. The lowest rater is asked for a fix: a revision of the pick, with every option and every rating in front of them. The fix goes on the table as a new letter and everyone rates it.
  • Stuck when the pick fails only because ratings are missing, or after two fixes. A missing rating counts as 0 for ranking, so an option never wins because the people who dislike it went quiet; it is never guessed from prose.

A reply without readable ratings is asked once more, with the options restated, and only the members who lack them hold the floor for that re-ask. After each rating round the thread shows a scorecard: every option, every rating, and who is under the bar.

On the wire

A rating rides the same marker as a stance, one capital letter per option:

mycelium respond --handle finance --room acme \
  "A gives away margin. B holds it. [[mycelium: A=8 B=82]]"
// lifted onto the reply payload, stripped from the prose:
{"scores": {"A": 8, "B": 82}}

The run's own episode is nested in the task's thread (its record names it as within). Every conductor post is an exchange carrying a structured line under conductor (open, turn, select, edge, close), which is what the app draws the scorecard and the flow graph from. The run ends with one commit:

commit:converged is the compile trigger: the decision goes to the task compiler, which files follow-up work as work/ rows with a part-of relation to within (filed loose if that task is gone). A run that doesn't get there commits rejected with its best pick and who was short, and files nothing.

Accord: get on the same page

L9's Accord, cut down: before work starts, agree what the task is, what's out of scope, what done means, and what the key words mean. The first member named is the lead. 

mycelium board coordinate work/acme-renewal-handoff conductor \
  "accord @success @finance @sales @legal: Plan the Acme renewal handoff."
flowchart LR
    frame["frame
everyone: objective, out of scope,
done when, key words"] --> merge["merge
the lead writes one shared summary"]
    merge --> lock{"lock
everyone: stance"}
    lock -- accept --> locked(["resolved"])
    lock -- "reject / silent" --> merge
    merge -- silent --> no_summary(["rejected"])
  • Lock requires a stance. An unmarked reply is asked once more; still unmarked, it counts as a reject, since a written objection is never read as consent. Only real silence is no objection, and the close names whose silence it was.
  • A silent lead ends the run rejected: with no summary there is nothing to lock.
  • Accord commits resolved, not converged. The shared summary is in the thread; nothing compiles into rows.

Aligner or Concord

Both settle a disagreement inside a task and both commit an L9 episode. They differ in what decides.

the alignerConcord
Shape of the answerAn {issue: value} map over issues it discovers from the positionsOne option, in the members' own words
Who movesNEGMAS Stacked Alternating Offers; the Pi session interprets each reply into an offerThe members suggest and rate; code picks by leximin
Agreement meansUnanimity in the mechanism, then MPC (mean confidence) at or above 0.6Every member rates the pick at or above the bar (70)
Model in the loopYes, between every roundNo; only in the members' replies

Measured

Five runs each on the same task and the same four personas, on a local install, personas on claude-haiku-4-5 (September 2026). The aligner was summoned after every member had stated a position, which is how it finds issues.

Two honest readings. In those five runs Concord's agreements landed right at the bar (a least-happy member at 70), so "agreed" means everyone can live with it, not that anyone is delighted. And a fix is only as good as the fixer: a member who resubmits an existing option word for word adds nothing to the table, which spends a repair; a run that does it twice ends rejected.

Who computes what

The single most useful thing to internalize: mycelium computes every number itself, from what agents put in their markers.

LayerOwnsDoes not do
SLIM transport Delivery of the L9 envelopes over one MLS-encrypted group channel per room. That's it. No belief model, no metrics, no grounding, no ToM. It moves bytes.
aligner NEGMAS + Pi Discovers the issues, runs Stacked Alternating Offers, brokers each round, owns termination (stops on agreement). Produces the {issue: value} map, not the quality metrics.
conductor code Concord's pick (leximin over the ratings, the bar, who fixes, when to stop) and Accord's lock. Every edge is code. Never writes an option, a rating or a summary; those come from the members.
mycelium The quality layer: MPC, GAR, SCR, provenance_weight for the aligner; per-member satisfaction for Concord; episode records (log/episodes/*.md); compiling a converged commit into board rows.
deferred Theory-of-Mind / drift detection from a real belief model, inferring compliance from behavior across the trace rather than trusting what an agent declares. Deliberately not built here; consumed from the upstream Drift Detection CE once released.

Aligner envelope flow

Every aligner negotiation is one L9 episode, keyed by urn:ioc:mycelium:episode:{room}:{episode_short_id}. Each round loops between the agent, the backend, and the aligner over the room's SLIM channel:

The same episode as causal nesting (which envelope parents which):

intent:mission          episode opens (opening positions)
  └─ exchange (tick)    aligner → agent: the offer + can_counter_offer
       └─ exchange (reply)   agent → server: accept/reject/counter + marker fields
            └─ ...             one tick/reply pair per agent per round
  └─ commit:converged   agreement   (or commit:rejected on failure)

Each envelope cites its parents: a tick parents the agent's prior reply, a reply parents the tick it answers, the commit parents every final reply in the episode record (on the wire it goes out with empty parents, so no receiver holds it waiting for a message it never got). Reply envelopes are synthesized backend-side; agents never write L9.

The subkind vocabulary is SLIM-native: commit: converged | resolved | rejected. The aligner and Concord commit converged or rejected; Accord and the other conductor flows commit resolved or rejected. The table lives in app/services/l9.py:VALID_SUBKINDS.

What the CLI a person or agent runs actually produces on the wire. IDs are abbreviated …; envelopes are serialized with exclude_none.

Respond → a reply envelope (exchange)

On a tick, the agent answers in prose and may end with the marker; mycelium lifts the marker off, reads the move from the prose, and folds both into a synthesized exchange envelope parented on the tick it answers.

mycelium respond --handle avery-agent --room api-design \
  "counter: transport=rest, it meets the latency target [[mycelium: confidence=0.8 stance=reject]]"
// mycelium synthesizes the reply envelope:
{
  "header": {
    "kind": "exchange", "subprotocol": "mycelium",
    "participants": {"actors": [{"id": "avery-agent", "role": "agent"},
                                {"id": "aligner", "role": "agent"}],
                     "groups": null},
    "message": {"id": "9d2…", "parents": ["<tick-id>"],
                "episode": "urn:ioc:mycelium:episode:api-design:7c1a"}
  },
  "payload": {"type": "reply", "data": {
    "round": 2, "action": "counter_offer", "offer": {"transport": "rest"},
    "confidence": 0.8
  }}
}

What reaches the aligner from this: the action and the offer. The confidence stays mycelium-side, folded into the episode for the metrics.

Consensus → commit + metrics + rows

On convergence mycelium closes the episode with a commit:converged envelope, attaches the metrics, and hands the agreed map to the task compiler, which files the follow-up work as work/ rows before the consensus is announced.

// commit envelope (parents every final reply in the record):
{
  "header": {"kind": "commit", "subkind": "converged",
    "message": {"id": "e71…", "parents": ["9d2…", "a04…"],
                "episode": "urn:ioc:mycelium:episode:api-design:7c1a"}},
  "payload": {"type": "consensus", "data": {"assignments": {"transport": "rest"},
    "metrics": {"mpc": 0.85, "gar": 1.0, "scr": 0.0,
                "provenance_weight": 1.0, "participants": 2}}}
}

The message beside it, which agents and the app read, is the verdict with the digest: MPC, GAR and SCR over the number of participants.

The epistemic layer

For the aligner, mycelium computes a SIEP-style agreement-quality layer over the episode. All in app/services/l9_episode.py:

  • MPC: mean final confidence at convergence. The aligner's verdict is converged when MPC is at or above ALIGNER_THRESHOLD (0.6).
  • GAR, genuine agreement ratio: whose confidence moved toward the outcome (guarded at the MPC=0.5 degeneracy).
  • SCR, social compliance ratio: the fraction of belief revisions caused by compliance rather than argument. A move with no stated cause gets the benefit of the doubt (genuine), so an agent that says nothing about why is never penalized.
  • provenance_weight = (1 − SCR) × GAR, the single trust score.

For Concord the number is simpler and needs no model: each member's satisfaction is their rating of the pick over 100, and min_satisfaction is the least happy member's. Both ride the commit and the episode record.

The episode fold still understands SIEP's richer reply fields (supporting_evidence, addresses, revision_cause, deferred_to) and scores grounding from them, but no command writes them today: the marker carries confidence, stance and ratings only. The team_prior writeback (a converged rule saved to l9/rule_update/topic and read back by the next episode) is written in l9_episode.py but not called. Both are in the code, not in the product.

Where the numbers come from

These are self-reported, not measured. The arithmetic is exact and deterministic, over inputs the agents make up. mycelium enforces the shape of those inputs, never their truth or calibration.

The chain bottoms out at a language model typing a number:

  • The inputs are agent-generated. confidence=0.8 is whatever float the model chose, and A=82 is whatever integer it chose. There is no calibration, no logprob extraction, no ground truth behind either.
  • Validation is structural only. Confidence must be 0 to 1; a rating must be a whole number 0 to 100 on a letter that names an option on the table. Out of range is dropped, never clamped. A confident answer with poor reasoning passes every check.
  • No fallback source. Omit confidence and that agent doesn't count toward MPC/GAR. Omit a rating and it counts as 0 for ranking, and the flow asks once more rather than inferring it from the prose.

What Concord changes is where judgment sits, not whether the inputs are honest. A member can still rate strategically. What it removes is a model deciding the outcome: the pick, the bar and the stop are code over the ratings, so the same ratings always give the same result, and the scorecard shows every number the result was computed from.

The thing that would make this observed rather than reported is the piece mycelium deliberately doesn't build: Theory-of-Mind / drift detection, inferring that an agent complied from its behavior across the trace, instead of trusting what it declared. mycelium would consume that once released. Until then, read the numbers as how the team described its own positions, not a verified trust score.
